## 主要结果

最低等级设为 `FATAL` 时，被过滤的 `LOGD_TAG` 中位数为 **2.39 ns/op**，
P95 为 **2.44 ns/op**，且预检确认 Tag 与正文参数均未求值。这个数字只代表
当前设备和优化构建中的 `errno` 现场保护、原子等级读取与分支合计成本。

当前 512 字节栈优先格式化与重构前 `vasprintf` 算法的同进程对照如下：

| 正文或格式 | 当前实现 ns/op | `vasprintf` ns/op | 中位数降低 |
| --- | ---: | ---: | ---: |
| 字符串 16 B | 90.95 | 112.75 | 19.3% |
| 字符串 128 B | 128.49 | 315.90 | 59.3% |
| 字符串 511 B | 156.24 | 359.50 | 56.5% |
| 字符串 512 B | 256.11 | 356.80 | 28.2% |
| 字符串 1024 B | 302.26 | 398.64 | 24.2% |
| 字符串 4096 B | 553.65 | 573.49 | 3.5% |
| 字符串 16384 B | 1584.20 | 1629.45 | 2.8% |
| 整数格式 | 184.41 | 203.24 | 9.3% |
| 字符串与整数混合 | 173.96 | 194.61 | 10.6% |

511 B 仍落在单次栈格式化路径，512 B 开始进入精确长度动态缓冲和第二次
格式化，因此边界处成本出现台阶。正文越长，动态分配和字符处理逐渐占主导，
两种算法差距随之收窄。本次数据能支持“短消息栈优先确有收益”，不能当作
其它设备或 libc 实现上的固定比例。

分片器结果反映的是来源前缀、换行扫描、UTF-8 边界和内存复制的库内成本：

| Case | 中位数 ns/op | P95 ns/op | 片段数 |
| --- | ---: | ---: | ---: |
| ASCII 64 B | 160.32 | 160.50 | 1 |
| ASCII 512 B | 204.76 | 205.00 | 1 |
| ASCII 4000 B | 538.10 | 539.67 | 2 |
| ASCII 4096 B | 549.45 | 550.32 | 2 |
| ASCII 8192 B | 936.72 | 938.94 | 3 |
| ASCII 16384 B | 1723.67 | 1725.00 | 5 |
| 多行 8192 B | 2270.25 | 2345.43 | 3 |
| UTF-8 8192 B | 937.26 | 939.18 | 3 |

多行正文需要反复识别逻辑行并添加来源前缀，所以同等字节数下明显高于单行；
UTF-8 Case 与同长度 ASCII Case 接近，说明当前安全切点扫描没有形成异常开销。

## 平台突发写入边界

7000 次真实 `LOGI_TAG` 突发调用中，外部观测到 4131 个携带调用标识的首片，
整体比例约 **59.0%**。长正文总体更容易出现首片观测比例下降；不同线程数之间
波动明显，当前数据不能支持“线程越多比例越低”之类的单调关系。就绪标记和
完成标记分别排除了采集启动与尾部排空的固定等待竞态；但当前生产日志后端不返回
写入结果给调用方，现有证据仍不能把缺失精确归因到某一个平台环节。

4000 B Case 会被拆成多个 logd 条目，而调用标识只在首片。因此这里的比例
不是“完整正文送达率”，即使首片已被观测，也不能由此证明后续分片全部留存。

平台 Case 的 `ns/op` 是整批墙钟时间除以总调用数，只表示突发写调用的聚合
返回速度，不是单条日志延迟。首片观测比例不足时，更不能把较低的 `ns/op`
解释成“成功送达更快”。详细逐组数据保存在同目录 CSV 中。

## 当前结论

1. 格式化前等级过滤的主要路径非常轻量，且参数短路语义成立。
2. 512 字节栈优先策略对常见短消息有明确收益；长消息收益收窄，符合实现结构。
3. 分片成本随正文长度、片段数和逻辑行数增长，UTF-8 安全切点没有出现异常退化。
4. 高频真实日志首先受到平台链路和留存能力约束；库内性能、首片观测与完整正文留存必须分层讨论。
5. 该结果适合作为当前提交在当前设备上的基线，不作为跨设备或 CI 绝对阈值。
